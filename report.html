專案執行摘要 (Executive Summary)

Cua 是一個旨在「為 AI Agent 提供真實可操作的電腦環境 (Give AI agents computers they can use)」的次世代開源基礎架構。它突破了早期 Anthropic 或傳統 RPA「單純透過螢幕截圖識別並暴力搶佔滑鼠游標」的侷限，提出並實踐了 Computer-Use 2.0 哲學。

Cua 將自動化表面解耦為三層：代碼執行面 (Coding Surface)、結構化工具面 (Tool-use / MCP Surface) 與 UI 自動化面 (UI Automation Surface)。其旗艦組件 Cua Driver 採用 Rust 打造，透過原生作業系統無障礙（Accessibility）與視窗路由機制，實現了業界罕見的「背景靜默操作（Best-Effort Background Execution / No-Foreground Contract）」，讓 AI 在操作計算機、辦公軟體或後台系統時，完全不搶奪使用者當前前景視窗與滑鼠焦點。

🎯
三大操作表面整合

AI 不必每個動作都點滑鼠。能跑 Script 就跑 Script，有 MCP/API 就調 API，只有在無 API 的原生桌面軟體才發動精確 UI 操作。

👻
不搶佔滑鼠與前景

業界首創「No-Foreground Contract」：使用者在終端機寫程式時，AI 可以在背景同時驅動 LibreOffice、計算機或特定視窗。

🖥️
全生態四位一體

涵蓋驅動核心 (Driver)、雲端沙盒艦隊 (Fleets)、Apple Silicon 虛擬化 (Lume) 與評測基準 (Cua Bench)。

2

核心用途與四大子系統架構

Cua 專門為需要橫跨不同應用程式、無公開 API 的專屬系統（如舊版 ERP、政府終端、本機 GUI 工具）以及跨軟體協同工作之 AI Agent 提供電腦操作能力。整個 Repository 分為四大支柱：

🚗
1. Cua Driver (本機桌面驅動核心)
Rust Core + UniFFI + MCP

用途：跨平台（macOS、Windows、Linux）後台桌面操控引擎。作為 Agent 與 OS 之間的介面，可透過 stdio MCP 直接串接 Claude Code、Cursor、Codex 等 Agent，或透過 Python / TypeScript 原生 SDK 呼叫。

  • macOS: Accessibility API + ScreenCaptureKit + SkyLight 路由。
  • Windows: UI Automation (UIA) + Win32 PostMessage 訊息佇列。
  • Linux: AT-SPI over D-Bus (純 Rust zbus) + X11 MIT-SHM / Wayland layer-shell。
☁️
2. Cua Fleets & Sandbox (雲端隔離沙盒)
Docker + Kasm + XFCE

用途：為不受信任的 Agent 或大規模平行批次任務提供完全隔離的雲端 Linux 桌面容器。Agent 可以在雲端隨選建立桌面（如 LibreOffice、Inkscape、瀏覽器）、執行自動化、截圖驗證並即時銷毀。

  • 支援資源池（Pools）預熱與動態認領（Claims）。
  • 內建 computer-server（Port 8000）提供遠端指令與 GUI 互動。
🍏
3. Lume (Apple Silicon 原生虛擬化)
Swift + Virtualization.Framework

用途：專為 Apple Silicon（M 系列晶片）設計的高性能 macOS / Linux 虛擬機管理工具。解決了以往 macOS 無法自動化建立乾淨環境的痛點。

  • 從官方 IPSW 映像檔一鍵安裝乾淨 macOS（Sonoma, Sequoia, Tahoe）。
  • 全自動無人值守設定（自動建立 lume 帳號、啟用 SSH、關閉休眠鎖定）。
  • 支援動態磁碟擴充與自動化 VNC 關閉 SIP (System Integrity Protection)。
📈
4. Cua Bench & Cua-S1 (評測與專用模型)
Evaluation + Trajectory Export

用途：標準化評估 Computer-Use Agent 能力的基準測試框架。提供無須虛擬機的模擬任務環境，自動驗證 Agent 完成度並輸出 0.0 ~ 1.0 Reward。

  • 匯出軌跡資料（Trajectories）供強化學習（RL）或監督微調（SFT）。
  • Cua-S1: 專為表格與介面操作研發的輕量專家模型（Dry-run 安全防護機制）。
3

核心特別功能與獨家技術亮點 (Key Highlights)

🛡️
1. No-Foreground Contract (背景靜默控制)

傳統 RPA 或自動化腳本執行時會強行將目標視窗彈至最上層並奪取滑鼠，使工程師無法同時工作。Cua Driver 顛覆此做法：

  • 不提升視窗 Z 軸：視窗留在被遮擋的背景中。
  • 不移動實體游標：實體滑鼠完全由使用者掌控。
  • 定向事件投遞：macOS 透過 AXPerformAction / SkyLight 路由；Windows 透過 UIA.Invoke / PostMessage；Linux 透過 AT-SPI DoAction。
🎯
2. 雙重感知單次返回 (Dual Perception)

在呼叫 get_window_state 時，Cua 同時回傳無障礙樹狀結構 (Accessibility Tree) 與高解析度視窗截圖：

  • 破解「a11y 說謊」：Electron 或 Webview 經常回報虛假狀態（已填入但畫面未更新）；雙感知允許 Agent 以視覺驗證結構。
  • 免重覆截圖切換：視覺定位（px）與語意定位（ax）共用同一快照，大幅減少延遲與 Token 消耗。
🪜
3. 階梯式自動降級階梯 (Action Ladder)

針對視窗動作，Cua 定義了極其嚴密的階梯式降級與反饋機制：

❶ 首選 ax 階 (語意): element_index 驅動，可驅動驗證，背景安全執行。
❷ 降級 px 階 (座標): a11y 缺失或空標籤時，直接按快照 (x, y) 點擊。
❸ 最後升級前景: 僅在目標僅接受實體 DirectInput 遊戲或 Canvas 時，啟用 delivery_mode: "foreground"。

每個動作回傳包含 verified: bool、effect: "confirmed" | "unverifiable" | "suspected_noop" 與機器可讀的 escalation 提示。

🎨
4. 獨立合成多游標圖層 (Multi-Cursor Overlay)

為實現直觀的人機監控，Cua 透過 tiny-skia、dotLottie 及 OS 圖層合成技術，在螢幕上渲染獨立的虛擬彩繪游標：

  • 游標不佔用系統硬體：使用者能清晰看見 AI 在哪裡點擊，而真實滑鼠仍在前景打字。
  • 多工作階段並行（Palette Sessions）：可分配不同顏色（crimson, amber, aqua, mint），支援數個 Agent 游標同時在多個視窗起舞。
🔒 原生安全性與權限模式 (Permission Modes)

Cua Driver 內建三種安全等級：standard（預設無彈窗操作）、bounded（僅允許 Manifest 宣告之白名單 App、特定目錄與網域）、unrestricted。若要附著已登入的 Chrome/Chromium Profile，必須明確宣告 --grant existing-profile，防止憑證遭 Agent 惡意竊取。

如何展示 Cua (Showcase & Demos)

展示 Cua 時，可以依據受眾與環境選擇以下三種極具震撼力的展示途徑：

🎯 展示範例 A：本機背景計算機閉環驗證 (最快 3 分鐘上手，適合一般展示)

展示效果：使用者在終端中執行指令或與 Claude/Cursor 對話，桌面上「計算機」在背景被打開，自動按壓 6 × 7 並驗證畫面顯示 42，過程中滑鼠游標完全不動，終端機焦點未被奪走。

步驟 1：安裝 Cua Driver

# macOS / Linux 一鍵安裝
/bin/bash -c "$(curl -fsSL https://cua.ai/driver/install.sh)"

# 啟動守護行程並授予系統權限 (macOS)
open -n -g -a CuaDriver --args serve
cua-driver permissions grant
cua-driver status
cua-driver doctor

步驟 2：測試底層 API 偵測運行中的桌面 App

cua-driver call list_apps

步驟 3：串接 AI Agent (以 Claude Code 或 Cursor 為例)

# 自動將 Cua Driver 作為 MCP 工具掛載至 Claude Code
claude mcp add --transport stdio cua-driver -- cua-driver mcp

# 在 Claude Code 輸入提示詞開始展示
> 請打開計算機，計算 6 乘以 7，並驗證螢幕上的運算結果是否為 42。
🔥 展示範例 B：National Records System 多游標多視窗並行 (視覺衝擊最強)

展示效果：螢幕切分為四個象限，分別運行 4 種不同 UI 技術架構的舊版檔案終端（Win32 GDI 無 a11y、.NET WinForms、.NET WPF、Electron）。中央由人類在 Master 終端點擊一次，周圍 4 個視窗瞬間出現 4 隻不同顏色（紅/黃/水藍/綠）的合成游標，同時在背景同步提交資料並跳動計數器，無任何視窗被拉抬到最上層！

# 位於本專案 samples/driver/multi-cursor 目錄下
cd samples/driver/multi-cursor
cargo build
dotnet build dotnet/winforms/winforms.csproj
dotnet build dotnet/wpf/wpf.csproj
npm install --prefix electron

# 啟動多視窗調度器展示
.\target\debug\orchestrator.exe --auto
🎵 展示範例 C：CUA Jukebox 電腦交響樂隊 (極致時序與控制展示)

展示效果：將一段 MIDI 音樂拆解為不同樂器軌道（大鼓、小鼓、Bass、琴鍵），每個視窗為獨立 Minigame 介面。背景的多個 Cua Driver 游標依據樂譜節奏，精確在幾十毫秒內點擊背景琴鍵與打擊板，透過 OS 音訊合成輸出完整多部合奏！展示 Cua 超乎尋常的並行事件調度能力。

# 位於本專案 samples/driver/jukebox
cd samples/driver/jukebox
cargo run
☁️ 展示範例 D：Cua Fleets 雲端桌面隔離沙盒 (企業與測試場景)

展示效果：透過 Python 呼叫 cua-sandbox SDK，在雲端動態認領（Claim）一台 Linux 容器桌面，背景啟動 LibreOffice Calc 填入資料，抓取截圖並將雜湊值回傳本機驗證，驗證完畢即刻銷毀容器，完全不影響本機環境。

# 安裝 Sandbox SDK
uv pip install cua-sandbox

# 執行雲端測試腳本 (位於 samples/python/1_fleet_throughput.py)
python samples/python/1_fleet_throughput.py

深度評估：適合 Embedded System（嵌入式系統）嗎？

⚠️ 核心結論先行 (Key Takeaway)

Cua 本身「極不適合」直接部署於傳統嵌入式系統、微控制器（MCU）或輕量 IoT 閘道器內部。
即使在具備螢幕的高階邊緣裝置（如 Raspberry Pi 5 或 Jetson），以 Cua 的「桌面視圖 + 多模態視覺 Agent」架構驅動嵌入式 HMI，在架構設計上也是極度過度設計（Overkill）且極不合適的。然而，若將 Cua 部署於外部主機，將嵌入式裝置作為「被測物（DUT）」進行非侵入式外部黑盒測試，則具有特殊潛力。

一、 嵌入式系統分類維度剖析矩陣

設備分類 代表硬體與架構 適配可行性 核心技術阻礙與矛盾點
微控制器 / 裸機 / RTOS STM32, ESP32, RP2040 (FreeRTOS, Zephyr) ❌ 絕對不可行 無 MMU、無作業系統等級進程、記憶體僅 KB 級。Cua 依賴 Rust tokio 非同步執行緒、D-Bus、圖形系統，完全無法編譯與運行。
無顯示無頭 Linux (Headless IoT) OpenWrt 路由器, 邊緣感測閘道器 (Buildroot / Yocto) ❌ 邏輯衝突 無任何圖形顯示（X11/Wayland）與無障礙匯流排。無頭裝置本就使用 CLI、SSH、REST API、MQTT 交互，引入 GUI Computer-Use 畫蛇添足且消耗資源。
專屬嵌入式 HMI / 觸控面板 POS 機、工控機、車載螢幕、醫療儀器 (Qt EGLFS, LVGL) ⚠️ 嚴重受阻 大多數嵌入式 GUI 為節省開銷與開機時間，直接寫入 Framebuffer / DRM-KMS（如 Qt eglfs），根本沒有 X11/Wayland 視窗管理員，更剝離了 AT-SPI D-Bus 服務。Cua 的 platform-linux 無法掛載事件。
高階邊緣單板電腦 (Edge SBC) Raspberry Pi 5, Jetson Orin (運行完整 Ubuntu Desktop) 🟡 理論可行但代價高 若編譯為 aarch64 且安裝標準桌面，cua-driver 本體可運行。但多模態 VLM 本地推論吃滿算力；若回傳雲端推論，頻寬與延遲無法滿足工控即時性（Real-time）。

二、 關鍵瓶頸與相依性衝突剖析

1. Linux 平台相依性過於龐大

查閱 libs/cua-driver/rust/crates/platform-linux/Cargo.toml，其底層緊密綁定：

  • atspi (依賴 D-Bus 系統守護行程)
  • x11rb / x11 (依賴 X11 MIT-SHM 共用記憶體)
  • wayland-client 與 wayland-protocols-wlr

嵌入式 Linux 系統為求極致精簡與開機秒開，通常會將上述套件完全裁剪。

2. 算力、記憶體與即時性 (Real-time) 矛盾

Computer-Use 的本質是「截圖 → 多模態大模型視覺推理 → 決策點擊」。

  • 邊緣算力不足：高解析度 VLM 推理一次動輒 2~5 秒，且需 8GB+ 顯存。
  • 頻寬浪費：連續傳送未壓縮/壓縮截圖至雲端大模型消耗大量蜂巢網路頻寬。
  • 缺乏確定性：嵌入式控制要求 Deterministic（確定性）與毫秒響應，大模型機率決策無法用於安全關鍵（Safety-Critical）工控。

三、 若要在嵌入式領域應用，何種場景才合理？

✅ 唯一具實用價值的切入點：外部非侵入式 QA 驗證測試台 (HIL Testing)

不要將 Cua 塞進嵌入式晶片中，而是將 Cua 作為「自動化產線質檢員」部署在測試電腦上：

[外部測試電腦 (執行 Cua + AI Agent)]
  ├── 影像輸入： 透過 HDMI 採集卡或工業相機讀取嵌入式裝置螢幕。
  ├── 控制輸出： 透過硬體模擬器（如 USB HID 模擬滑鼠/鍵盤、串口、CANoe）傳送事件。
  └── 目標被測物： 實體 POS 機、車載中控儀表板、醫療儀器 (免修改任何韌體程式碼)。

在此架構下，Cua Bench 可負責比對 UI 回饋並計算任務成功率，實現免侵入式、純視覺黑盒的自動化迴歸測試。

💡 總結研判與架構決策指引
  1. 如果您是開發桌面端 AI Agent：Cua 是目前開源界在處理「真人協同作業（Human-in-the-loop）」體驗最為極致的框架。它的「No-Foreground」背景驅動能力，解決了過去所有桌面 Agent 動態操作時直接癱瘓使用者電腦的致命硬傷。
  2. 如果您想為 Agent 提供隔離執行環境：Cua 旗下的 Lume（針對 Apple Silicon macOS）與 Fleets（針對 Linux 容器）提供了無人值守與雲端彈性銷毀的標準解法。
  3. 如果您從事嵌入式或邊緣物聯網開發：請勿嘗試把 Cua 塞入微控制器或無頭網關。針對嵌入式 HMI 自動化，優先採用 uinput 核心驅動模擬、Linux Event 節點或 Qt Test 測試框架；若需要 AI 視覺自動檢驗，請採用「外部主機跑 Cua + 影像擷取卡」之黑盒測試架構。
